fix(resume): the resume guard sees holders by open fd, not only by argv; drifted rows reset to birth

Two units from the 2026-09-04/05 collapse nights, both generalized across
every self-minting CLI (Codex, Claude Code, Muse, Antigravity, ...):

- The external-holder scan was argv-only: it matched processes whose command
  line names the session id. An interactive TUI runs as `codex -s
  danger-full-access` and holds its rollout and writer lock purely by fd -
  exactly the holder class orphaned by daemon rotations was invisible, the
  resume composed into a held thread, and codex refused with its own raw
  -32600 ("already has an active writer"). The scan now also walks /proc fds
  for any open path carrying the session id and classifies holders as
  before (environ marker / ancestry), so the existing wait + named banner
  ("orphaned process ... kill <pid>") covers them.

- A drifted row whose attempts exhausted with no vouched alias kept
  advertising a transcript it does not hold, and resume kept racing a
  foreign writer. When the id is dead (fd-live nowhere) or the owner alias
  hands it to a DIFFERENT row's birth, the poll now resets the row to the
  birth id its path still carries and clears the stale Codex Session
  metadata (cli/agent_identity_reset_to_birth, named because).

- The Muse/Antigravity stamp chore gets the codex chore's handover
  treatment: the terminal pid resolves through the preserved owner before
  giving up, unresolvable rows are named, and a duplicate transcript bind
  is refused - "a new session opens in the spot after restart" was this
  chore silently skipping every row across a takeover.

Tests: fd-holder found while a real child process holds the transcript with
no session id in its argv; reset-to-birth clears drifted id + stale
metadata and never moves a birth row.
