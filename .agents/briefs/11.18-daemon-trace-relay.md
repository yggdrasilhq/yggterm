## What Landed (M1 + M2)

### M1 — NAME THE LOCK HOLDER ✅

Added `lock_holder_trace` module + integration into daemon request flow:
- Thread-local state tracks which request holds the runtime lock
- When lock is acquired: `enter_lock_holder(request_name)`
- When lock is released: `exit_lock_holder()` emits span with held duration, remote call count, total remote time
- When a request waits on lock: `lock_wait_identified` trace now includes who was holding it

**Example traces:**
```json
{"name": "lock_wait_identified", "payload": {
  "waiting_request": "Status",
  "wait_duration_us": 10150000,
  "lock_held_by": "Snapshot",
  "lock_held_for_ms": 10240
}}

{"name": "lock_holder", "payload": {
  "request": "Snapshot",
  "held_ms": 10240,
  "remote_calls": 4,
  "remote_call_total_ms": 9850
}}
```

**Code changes:**
- `crates/yggterm-server/src/lock_holder_trace.rs` (new)
- `crates/yggterm-server/src/daemon.rs`: integrated at lock acquisition and release points
- `crates/yggterm-server/src/lib.rs`: declared module

### M2 — DETECT BLOCKING CALLS INSIDE LOCK ✅ (first of three instances)

Wired `working_flags` proxy calls in snapshot handler:
- Records calls > 50ms as `blocking_call_inside_lock` trace
- Payload: lock holder, holder duration, call cost, peer label, running totals
- This is the #1 culprit (the snapshot fan-out fix in 633e22d8)

**Example trace:**
```json
{"name": "blocking_call_inside_lock", "payload": {
  "lock_held_by": "Snapshot",
  "lock_held_for_ms": 10000,
  "call_name": "working_flags",
  "call_cost_ms": 1050,
  "peer": "daemon-on-machine-b",
  "total_remote_calls_in_span": 4,
  "total_remote_time_in_span_ms": 9850
}}
```

**The key question answered:**
If the snapshot deadlock existed today and nobody read source code, traces would show:
1. `lock_wait_identified`: waiting request ID'd holder by name
2. `lock_holder`: holder duration + work inside
3. `blocking_call_inside_lock` × 4: all calls were inside the lock (they should never be)
4. Correlated with `proxied_working_flags_slow_peer`: each peer call > timeout

## What Remains (M3 + M4)

### M3 — INSTRUMENT DISCONNECT/RECONNECT ⚠️

The GUI shows "Recovering Local Terminal" toasts. Daemon side needs:
- `daemon/lifecycle/client_disconnected`: when client closes (reason, active sessions)
- `daemon/lifecycle/recovery_initiated`: when daemon detects a client is back
- `daemon/lifecycle/recovery_complete`: after sessions restored (count, time)

**Strategy:** Hook into client connection lifecycle in daemon.rs (client accept loop, stream close handlers).

## Measured Impact (from 633e22d8)

The defect this observability targets:
- `daemon_request/snapshot` p50/p95 both pinned at 10,060–10,239 ms (the 10s timeout)
- ~128 snapshots over 2 hours
- ~21 minutes of daemon deafness with requests queued behind the lock
- User-visible: typing stops

With these traces:
- The next time a similar defect occurs (or the p50/p95 spread widens again), it shows up as:
  - High `lock_holder/held_ms` values
  - Multiple `blocking_call_inside_lock` records under the same lock holder
  - `lock_wait_window` correlating with `lock_holder` for the same request name
