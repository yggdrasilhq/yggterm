### ⛔ S1's CLOSING CLAUSE — "then it retires on its own" — AND WHERE IT CAN FAIL

The drain is *move sessions off, then let the emptied daemon retire.* The second
half is a real dependency, and a sibling lane has one counter-example: a sandbox
daemon with the gates apparently open **lived 48 minutes against a 90 s window**.

`daemon_should_idle_shutdown` has **three gates**, and reading it explains that:

1. `terminal_session_count > 0` ⇒ never retire. ⚠ **This counts OWNED +
   PRESERVED**, so a daemon holding only bequeathed records still refuses.
2. not yet idle for `idle_shutdown_ms` ⇒ no.
3. `active_client_instance_records` empty ⇒ retire. **Otherwise it retires only
   if `daemon_is_superseded(home_dir)`.**

⇒ **Gate 3 is the one the drain rests on.** On dev every legacy daemon IS
superseded, so once its hands are empty it should go. **A sandbox typically has
no superseding daemon**, so gate 3 fails and an emptied daemon lingers for ever —
which would explain the 48-minute observation without any defect in the drain.

would make `subscribe` refuse that row ever after, turning a benign timeout into
a permanent disarm.

⛔ **`tick --dry-run` was mutating** — the quota-dead path appended to the
retired ledger and deleted the subscription with no guard, while every other
mutation in the tick has one. The command someone reaches for *because* they are
unsure was the one quietly retiring rows.

⚠ **This lane's three UNKNOWNs at 11:22 were that defect, caught in production:**
their subscription files had been deleted with no trace by the pre-fix watcher
running since 09:29. ⇒ **After changing this script, RESTART the watcher and
verify by md5 of the file at the process's own `/proc/<pid>/cwd`** — a pull
alone changes nothing, because Python already loaded the old file.

### ⛔⛔ TWO THINGS THE ARMING ITSELF COST, BOTH MINE, BOTH ON 2026-08-14

1. **ARMING A ROW THAT READS `busy: true` GETS IT BOOTED.** I armed 6.7 and 2.2
   from `coverage`'s own remedy (*an unattended delegate → subscribe*). Within
   seven minutes the tick recorded **`boots=1` against 6.7**, and both lanes
   unsubscribed themselves — 6.7 with `--force`, because a monitor refuses.
   ⇒ **`coverage` classifies; it does not tell you the row is STALLED.** Read
   `busy`/`busy_reason` from `server app rows` AND the last timestamped record
   before arming, and when a lane unsubscribes itself afterwards, **leave it** —
   re-arming is fighting their decision, not triaging. They are UNKNOWN again on
   purpose, and that is the design: a plain `unsubscribe` records nothing so the
   row gets re-triaged by someone who looks.
2. **A RESTART CAN LEAVE TWO WATCHERS, AND TWO WATCHERS DOUBLE EVERY BOOT.**
   Killing the old one opened a window in which another lane started its own; I
   then started mine, and for a minute there were two. ⭐ **`booter.pid` and the
   heartbeat are the arbiter** — after any restart, enumerate every
   `ygg-booter.py watch` process by argv[0], keep the one the pidfile names, and
   kill the rest. ⚠ Do not count with `pgrep -c`; it counts your own shell.

### ⭐ THE TRIAGE PROVED THE WHOLE PATH, AND EXPOSED ONE HOLE BY DOING SO

The one row I subscribed was a stalled delegate. Twenty minutes later the booter
**woke it** — `boots=1`, the `continue` is in that row's transcript at 03:52:14Z,
and it has written 43 records since. **Subscribe → boot → resume works, on a live
row, end to end.**

⛔ **Then it unsubscribed ITSELF four seconds later** — the "am I done?" answer
`cmd_unsubscribe` already refuses, and refuses **only for monitors**. The wake
worked and the watch died in the same minute. ✅ Fixed: a subscription whose row
is not the caller now defaults to `monitor`; an explicit `--kind` still wins.
Both live delegates on that lane were re-armed under the new default and read back
`monitor`.

⚠ **UNKNOWN is a FLOW, not a state you finish.** It was 0 at 09:04 and 7 at
09:44 — rows appear, and rows the tick unsubscribes reappear. Of those 7: two had
**no transcript at all** (just-spawned seats that will subscribe themselves on
claim — do not retire a row that has not had time to exist), and three were
fintax rows another lane had just unsubscribed while reworking the rate-limit
hold. ⛔ **Do not re-arm rows another lane is mid-change on** — that is fighting
their work, not triaging.

## SECTION 7 — THE DISCIPLINE THAT ACTUALLY PAID

- **Falsify your own test before trusting it.** Every fix here was run against a
  mutant that disabled it, and each failed with the original symptom first.
- **Both controls in the same run.** The pty-thread proof and the persist-drop
  proof both *passed* — and proved nothing, because the negative control passed too.
- **A finding is not a mechanism.** Three deaths with a matching signature is
  still coincidence in time until an exit path is traced.
- **Read the artefact, not the exit code.** A fabricated uuid reached a ledger
  whose entire value is being trusted, and only the read-back caught it.
- ⭐ **The instrument's silence can be STRUCTURAL rather than evidential** — a
  crossing that checks one direction reports "0 warnings" over the hole it cannot
  see. Pair that with "a control that also passes supports nothing".
