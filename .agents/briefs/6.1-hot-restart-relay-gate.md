## SECTION 3 — THE DRAIN: UNBLOCKED, NOT YET EXERCISED

### ⛔⛔ JUSTIFY S1 CORRECTLY OR IT WILL LOOK LIKE A FAILURE

**There is no leak.** A daemon whose sessions are QUIET costs ~0.67 ms per
request and its reader threads cost nearly nothing. The bursty cost is **one pty
reader thread per session, proportional to that session's OUTPUT VOLUME** — so
**the daemon population is expensive because it is BUSY, not because it is old
or numerous.** That is the second independent line ruling out a leak.

⇒ **The drain moves work onto fewer, CURRENT daemons. It does not remove work.**
Anyone selling S1 as *"reclaim leaked cores"* is promising a saving that will not
arrive, and its absence will read as the drain having failed. ⛔ **Do not send
anyone leak-hunting in the daemon.**

### ⭐⭐ CORRECTED 2026-08-14 — IT DOES REMOVE WORK, AND THE IDLE ONES ARE THE COSTLY ONES

The paragraph above is right that there is no leak and right that sessions
themselves must be *moved* rather than deleted. It is **wrong that nothing is
reclaimed.** Measured passively over 60 s windows, each daemon against its whole
process subtree:

| | cores | its subtree |
|---|---|---|
| 10 legacy daemons, sockets bound, 73–246 rows | **~2.5** | essentially **idle** |
| 2 current daemons, ~200 descendants between them | **0.26** | **2.3 cores of real work** |
| 3 daemons that lost the bind lock (no socket) | **0.000** | idle |

⇒ **The current daemons are the cheap ones and the legacy population is
idle-but-burning**, so for that population the cost is not session work and
draining genuinely reclaims it. ⭐ **A daemon nobody can reach costs nothing**,
which makes the apparent per-daemon floor a property of *being reachable while
holding a row inventory* rather than of being a daemon — and reconciles the
population model's intercept with the request path having no floor inside it.

⛔ **Do not price this from `/proc/<pid>/task`:** per-thread accounting saw 0.054
cores against a process total of 0.281, because the work lives in threads that
exit inside the window. ⚠ And do not guess the mechanism — the per-connection
figure is orders of magnitude too small, and *what sets the poll rate* is open in
another lane.

⭐ **First target, confirmed in the act:** the 2.12.14 daemon re-reads **69 MB/s**
(all page cache, zero disk) with three IDLE shells attached, against 0.15–1.20
MB/s everywhere else — the full-corpus-read defect running on a version older
than its fix. ⚠ Its three sessions are plain shells, which the migration path
refuses, so retiring it is an owner-facing question about three shells rather
than a migration problem to solve.

⭐ **The real reasons S1 is still right, and they are enough:** legacy daemons
lack every fix since their own version (and that grows with each release), they
carry frozen row inventories they do not own, and — the one this session
proved — **they are where the fatal handover paths live.**

⛔ **Do not quote any per-session core figure.** The sandbox number came from a
saturated pty (`yes(1)`), which no agent CLI approaches; live per-thread figures
are 0.02–0.19 cores. **The transferable claim is the SHAPE, never the magnitude.**

**Why the 14 legacy daemons never empty their hands:** one poisoned session pins
all of them. `classify_handoff_sweep` takes a `first_failure` and stops, so a
single stuck key held **eleven** healthy runtimes hostage (`readers_stood_down:
11, moved: 0`). Both halves are now fixed: `22f97c41` stops the key getting stuck that way, and
`de9cf741` stops one stuck key abandoning the rest — the loop attempts every
session and classifies at the end. ⚠ `Partial` is therefore much more common, and
`Partial` must NEVER exit the process; the code already knows that, but any
future edit there must keep knowing it.

⚠ **A "release" in `progressive_migration` KILLS the pty and re-resumes** — read
`release_session_for_migration`'s docstring before calling it a move. And it is
gated on being re-resumable, so **a plain shell can never be released that way**;
those daemons say so themselves (*"a plain shell with no store to resume from; a
cold shutdown would destroy it"*).

⇒ The drain cannot be exercised until 3.0.155 deploys. **Do not evict anything.**

### ⛔ S1's CLOSING CLAUSE — "then it retires on its own" — AND WHERE IT CAN FAIL

The drain is *move sessions off, then let the emptied daemon retire.* The second
half is a real dependency, and a sibling lane has one counter-example: a sandbox
daemon with the gates apparently open **lived 48 minutes against a 90 s window**.

`daemon_should_idle_shutdown` has **three gates**, and reading it explains that:

1. `terminal_session_count > 0` ⇒ never retire. ⚠ **This counts OWNED +
   PRESERVED**, so a daemon holding only bequeathed records still refuses.
2. not yet idle for `idle_shutdown_ms` ⇒ no.
3. `active_client_instance_records` empty ⇒ retire. **Otherwise it retires only
   if `daemon_is_superseded(home_dir)`.**

⇒ **Gate 3 is the one the drain rests on.** On dev every legacy daemon IS
superseded, so once its hands are empty it should go. **A sandbox typically has
no superseding daemon**, so gate 3 fails and an emptied daemon lingers for ever —
which would explain the 48-minute observation without any defect in the drain.

### ✅ SETTLED 2026-08-14 — AND THE GATE ORDER ABOVE IS WRONG IN ONE DETAIL

**Measured, not read:** an emptied daemon in an isolated home **retired at
exactly t+20 s against a 20 s window** and logged `idle shutdown`; the control
arm — same probe, same binary, 300 s window — was **still alive at t+200 s**. So
the probe can report both outcomes, and **S1's closing clause holds for the case
the drain actually produces: no sessions, no client records ⇒ it goes.**

⛔ **Correction to the gate reading above.** Supersession is NOT what an emptied
daemon rests on. The order is: sessions > 0 ⇒ never · not idle ⇒ no · client read
`Err` ⇒ **no, and now traced** · **records EMPTY ⇒ RETIRE** · records exist ⇒
retire only if `daemon_is_superseded`. ⇒ Supersession matters **only when client
records still exist for that endpoint**, so the 48-minute sandbox observation can
only be explained that way if that daemon HELD client records. On dev both roads
lead home: legacy daemons are superseded anyway.

⚠ The probe's own first version measured **nothing** — an empty `$PID` made
`[ -e /proc//cmdline ]` normalise to `/proc/cmdline`, the kernel command line,
which always exists, so a daemon that had already exited read as alive. A
liveness probe that cannot fail is not a probe.

⭐ **AND THE FAIL-CLOSED EDGE WAS THE WRONG WAY ROUND — I HAD IT BACKWARDS.**
I first reported that an error keeps a daemon alive silently. The caller's error
arm exists, but **the callee could never reach it**: every failure ended in
`return Ok(())`. So the real defect was the OPPOSITE and far worse — an
unreadable client-instances directory (permissions, fd exhaustion, ENOMEM) read
as **no clients**, satisfied gate 3, and **PERMITTED a daemon to retire while a
client was still attached to it**. Two halves of one decision disagreed about
what unreadable means, and the careless half won. Caught by the resource lane.

✅ Fixed: **absent stays `Ok`** (a real answer — no directory, no records),
**unreadable travels as `Err`**, and so does an incomplete listing or a record
that cannot be read. That also makes `b4f46302`'s trace REACHABLE, which it was
not when I wrote it. ⚠ The two changes only make sense together.
