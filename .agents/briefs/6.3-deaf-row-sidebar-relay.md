## THE TWO ITEMS THAT ARE ACTUALLY OPEN

### 1 + 3 — they share one apparatus, do them together

To see the amber dot you must manufacture a genuinely deaf row; that same row
is the only thing that can answer whether 12 s is right. You will not get one
cheaply twice.

- The reproducer that is known to work: `kill -STOP` the CLI process of a row
  **you created** (`--purpose`, `--ephemeral`). Alive, composer drawn,
  consuming nothing — the wedge's exact signature.
- The gap is `last_activity - last_output`, and `last_activity` is stamped by
  the WRITER. So you must **write to the row** after STOPping it, or the gap
  never opens.
- ⚠ A healthy child echoes in milliseconds — even a keystroke it means to
  ignore. So the false positive to measure against is a child with **echo
  off** (a password prompt), not a slow one.
- Read it back with `server app rows`, which emits `input_unanswered_ms` and
  `wedge_suspected`.
- `kill -CONT` and remove the probe row afterwards
  (`server app session remove`, GUI host only).

⛔ The GUI host is sequenced by 6.0. Ask before deploying or cycling; a
measurement window must never straddle a deploy.
⛔ *** runs 3.0.148, which **predates** the wiring. A deploy is required before
any live proof means anything. `scripts/deploy-fleet.sh --preflight` FIRST —
the ancestry gate is asked before the build only if you ask it.

### 2 — the right rail (`627f605e`), blocked on a missing instrument

The entry carries the measurements. The one thing that would settle it does not
exist: **there is no read-only DOM query in the app-control surface.**
`server app chrome` offers only `type`, and its `--assert <selector>@<attribute>`
is the sole DOM read but types first, so it cannot be pointed at a live GUI.

⇒ **Build the read-only chrome query.** That is the prerequisite, and it is
worth more than this one bug: every future "the chrome renders wrong" question
needs it.

The shape to test once you have it: `SideRailShell`'s own signature warns that
the host must emit a FIXED style key set across every mode, because *Dioxus
applies `style` property-by-property and does not clear dropped keys*. A key
emitted in one mode and absent in another lingers — which would survive every
later mode change (matching "hours") and leave the card painting while its
contents collapse. **Not confirmed. Do not inherit it.**

## METHOD NOTES THAT COST SOMETHING TO LEARN

- ⛔ **A revert harness must not use git.** `git checkout -- <file>` reverted
  ~120 lines of uncommitted work, not just the stub it was meant to undo, and
  `git status` then looked clean. `cp` the file aside instead, and commit a
  `wip` checkpoint before running anything that writes to your source.
- ⭐ **Exclude the confound before the diagnosis.** The window is composited
  transparent, so "that band is wallpaper showing through" would have explained
  the whole symptom. Ink fraction settled it: wallpaper has no near-black text
  pixels, the left tree has 0.79 %, the rail has 0.00 %.
- ⭐ **A privacy constraint and a faithful pixel are compatible.** Capture the
  full frame on the GUI host, crop it THERE, and fetch only the crop — the
  frame with the owner's session in it never leaves his machine, and
  `capture_faithful` still applies. Numeric probes (`ink_fraction`,
  `edge_energy`, one scanline of hex) answer "is anything drawn" without
  looking at content at all.
- ⚠ **`submitted: false` is a refusal, not unreachability.** A busy row will not
  echo, so `terminal submit` hammers it for the full timeout. Two tries, then
  use the peer plane. (Root cause now filed by 6.7: the readiness probe types
  over the human.)
